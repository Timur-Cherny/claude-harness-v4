# Отчёт для бизнеса и QA

Отчёт читает человек, который не был при прогоне и не может переспросить. Всё, что можно понять двояко, будет понято неверно — обычно в пользу «всё хорошо». Правила ниже выведены из ревью настоящего отчёта: каждое соответствует месту, где читатель споткнулся.

## Структура: четыре блока, не смешивать

Самая частая поломка — смешение уровней анализа в одном потоке: результаты первого прогона, второго и найденные дефекты идут вперемежку, и читатель постоянно переключает контекст.

1. **Прогон №1** — что, когда, с какими цифрами.
2. **Прогон №2** (если был) — то же, с явной границей.
3. **Найденные проблемы** — отдельным блоком, не вкраплениями.
4. **Итог и что дальше** — вывод, уверенность, остаток работ.

Внутри блока прогона всегда: состав окружения → что проверялось → числа → что сломалось.

## Числа

**Каждый показатель — с объёмом выборки.** `p50 35 мс, p90 45 мс, max 45 мс` без числа измерений читается как статистика, а на деле может быть десятью замерами, где p90 совпал с максимумом. Писать: `по 13 измерениям`.

**Набор перцентилей единый.** Если в одной таблице `p50/p90/max`, а в другой `p50/p90/p95` без максимума — читатель ищет подвох. Либо одинаково везде, либо явная оговорка почему.

**Любое соотношение, которое выглядит странно, объясняется на месте.** «13 заказов → 30 записей outbox» — законно (несколько смен статуса на заказ), но без пояснения выглядит как дубли. Правило: если два числа в отчёте относятся друг к другу не один к одному, рядом стоит фраза, объясняющая множитель.

**Подозрительно красивые совпадения комментируются.** «13 сканов при 13 заказах», «ноль нарушений по всем инвариантам» — верные цифры, но ревьюер спросит. Один короткий комментарий снимает вопрос: почему один скан на заказ, какой объём данных стоит за нулём.

**За каждым заголовочным числом — способ его перепроверить.** Ссылка на файл с запросом в `data/` или сам SQL. Число без источника — заявление, а не результат.

## Формулировки

**«Дефектов не выявлено» почти всегда неверно.** Если по ходу найдены дефекты наблюдаемости, персональные данные в метриках или отсутствие следа отказа — писать точно: *«дефектов бизнес-логики не выявлено»*, и рядом перечислить, какие выявлены.

**Утверждения о полноте проверять на полноту.** «Все пики пишутся в базу» звучит как «пишутся корректно», хотя 28 записей из 71 ушли без склада. Правильно: *«пишутся все, у части атрибуция неполна — столько-то»*.

**Данные верны, а панель их не показывает — это отдельный тип проблемы.** Не «метрика неверна», а *«данные корректны, дефект визуализации»*. Иначе читатель решит, что цифрам нельзя верить.

**Светофор отражает состояние компонентов, а не качество продукта.** «Три из трёх зелёные» рядом со списком из четырёх найденных проблем создаёт ощущение подлога. Оговорка обязательна: что именно измеряет каждая лампа.

## Величины, которые путают

Если в отчёте есть две похожие по смыслу, но разные по природе величины — задержка операции и длительность стадии, счётчик строк и счётчик событий, — **пояснение ставится сразу после первой из них**, а не в конце документа. К моменту, когда читатель дойдёт до сноски, он уже сделал вывод.

## Собственные ошибки — в приложение

Раздел «мы ошиблись в измерении и вот как это выяснилось» повышает доверие у инженера и снижает у руководителя: часть читателей поймёт это как «инструменту нельзя верить». Такое выносится в приложение **Lessons Learned** в конце, а в основном тексте остаётся результат.

При этом **скрывать ошибку нельзя**: она должна быть в документе, просто не в середине потока выводов.

## Сборка PDF

HTML печатается в PDF через headless-Chrome (`Page.printToPDF`, `printBackground: true`, A4, поля ~12 мм). Обязательный блок print-стилей, иначе страницы рвутся:

```css
@media print {
  table, figure, .kpi, .note { break-inside: avoid; }
  h2, h3 { break-after: avoid; }
  .grid { grid-template-columns: repeat(4, 1fr); }
}
```

Без него: таблица разрывается между страницами и строка уезжает в отрыве от шапки; заголовок остаётся сиротой наверху страницы, а картинка под ним уходит на следующую (страница заполнена на 40%); плитки показателей ложатся 3+1.

**Проверять результат фактом, а не видом:** число страниц, наличие картинок внутри (`pdfimages -list`, не по размеру файла), извлекаемость текста (`pdftotext`), и что светлая тема форсирована — иначе тёмная даст белое по белому.

## Чего не делать

- Не подавать выводы без объёма выборки — на маленьких числах любой процент врёт.
- Не хоронить оговорку о величинах в конце документа.
- Не писать «всё зелёное», если рядом список проблем.
- Не публиковать кадр, на котором значение не совпадает с текстом отчёта.
- Не заменять пропущенный артефакт плейсхолдером: писать, чего нет и почему.
