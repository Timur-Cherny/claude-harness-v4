# friction-review — превращение повторяющихся граблей в предохранители

Цель контура: **планку качества держит машинерия, скорость даёт модель**. Этот скилл — тот узел, где повторное трение конвертируется в детерминированную проверку, после которой ни одной модели уже не нужно про эту проблему помнить.

Полная спека контура: `~/nc-claude-brain/specs/SPEC_FRICTION_LEDGER.md`.

## Что читать

1. `~/.claude/exec-telemetry/personal-friction.jsonl` — записи `SubagentStop` (`capture-friction.sh`, `adapter: claude-friction/1`). Поля: `ts` (UTC), `executor`, `source_class`, `session`, `agent_id`, `agent_type`, `outcome`, `verification_state`, `friction_state`, `missing_reason`.

   **Это метаданные, а не трение.** `friction_state` равен `unavailable` во ВСЕХ записях, и `missing_reason` объясняет почему: Claude не отдаёт структурированного поля трения, а разбирать приватный текст отчёта адаптер не имеет права. Поэтому телеметрия отвечает на вопрос «кто и с каким исходом отработал», но НЕ на «на что наткнулся». Классификация трения берётся из источников 2-3 и из отчётов при приёмке — не из журнала. Считать долю прогонов с секцией «Трение» по этому файлу нельзя: там нет такого факта.

   Легаси-журнал `friction-raw.jsonl` (v1, поля `scope`/`trace`/`friction_section`/`repeat`/`signature`) **удалён из репозитория 02.09.2026**: `capture-friction.sh` перестал в него писать ещё в v2, и спека указывала на источник, который контур не обновляет. Замеры, сделанные по нему до этой даты, остаются в `worklog.md`, `graph/incidents/` и context-pack'ах как исторические — они верны для своего окна и не пересчитываются.

2. `~/nc-claude-brain/graph/incidents/*.md` — уже заведённые инциденты (`root_cause`, `pattern`, `severity`, `regression_guard`, `status`).
3. `~/nc-claude-brain/graph/patterns/taxonomy-*.md` — таксономия повторяющихся паттернов.

Читать **срезами**, а не целиком: сырой журнал растёт линейно, брать последние N записей или период.

## Порядок разбора

### 0. Префильтр возраста — до чтения журнала, 0 токенов

```sh
~/nc-claude-brain/scripts/friction-prefilter.sh   # порог: FRICTION_AGE_DAYS (дефолт 14)
```

Печатает узлы графа в `status: open/candidate` старше порога и журналы с невыполненным
date-обязательством (EVAL.md без прогонов, спека с непересмотренным статусом). Всё, что
он вывел, идёт в отчёт отдельным блоком **«[Т] висит без решения»** с возрастом — эти
пункты машинкой не закрываются, их только показывать при каждом разборе, пока не решены.
Пустой вывод — блока нет. Свежие узлы (< порога) в блок не тянуть: старение считается,
а не оценивается.

### 1. Сгруппировать по подписи, а не по времени

Один и тот же `signature` в разных сессиях — это не два случая, а один системный дефект. Считать повторы машинно (поле `repeat` уже посчитано хуком), не на глаз.

Подпись — не первая строка прозы, а набор артефактов, названных в секции (`tokens`): пути, команды, символы, всё в бэктиках. Формулировка у каждого агента своя, а имя файла при одной причине совпадает. Поэтому `repeat` считается по пересечению наборов, а не по равенству строк: совпало два независимых артефакта — та же причина. Одинокий общий токен за повтор не берётся.

**Пустой `signature` при `friction_section: true` и `files > 0`** (поле `vacuous`) — секция есть, но ни один артефакт не назван. По спеке это гипотеза «трения не было», а не факт; такие записи разбирать наравне с остальными, а не считать чистыми.

### 2. Применить матрицу эскалации

| Уровень | След есть (`trace: true`) | Следа нет (`trace: false`) |
|---|---|---|
| function | молча в реестр | молча в реестр |
| module, впервые | молча в реестр | инцидент `status: open` |
| module, повтор | **к пользователю** + проект предохранителя | **к пользователю**, предохранитель обязателен |
| domain | **к пользователю всегда** + предложение в пайплайн и скилы | **к пользователю всегда**, явно «решение слабое, вот почему» |

Правило без исключений: **решение считается качественным только при наличии следа в диффе** — теста, ассерта, констрейнта, индекса или хука.

С 20.08 след градуирован и считается по СОДЕРЖИМОМУ добавленных строк, а не по пути файла: `constraint` (миграция с CHECK/UNIQUE/индексом) → `assertion` (живой ассерт среди добавленных строк) → `guard` (хук, ПОДКЛЮЧЁННЫЙ в settings.json) → `none`. Спек-файл без ассертов, закомментированная проверка и миграция с одной новой колонкой следом не считаются. **Доменный уровень закрывается только `constraint` и `assertion`** — `guard` для него недостаточен.

Записи ДО 20.08 несут булев `trace`, посчитанный по пути файла: он завышен (97 срабатываний, из них 35 в работах без заявленного трения). Долю со следом за периоды до и после 20.08 не сравнивать — считались разные вещи. Формулировка отчёта на оценку не влияет. Основание: самоотчёт агента о конфигурации 25.07 утверждал «11 хук-скриптов» под шапкой «собрано чтением файлов», по факту их 12 и зарегистрировано 10.

### 3. Выбрать тип предохранителя под форму риска

Как в БД разные индексы под разную форму данных, так здесь разные ворота под разную форму риска. Сверху — сильнее:

| Форма риска | Предохранитель |
|---|---|
| уникальность, ссылочная целостность | констрейнт / уникальный (в т.ч. частичный) индекс |
| сохранение суммы, монотонность | property-тест или ассерт в коде |
| порядок операций, конкурентность | адверсариальный агент на Gate 2 + тест-сценарий |
| процесс, окружение, ресурсы | хук (`PreToolUse` / `PostToolUse` / `Stop`) |
| знание, которое некуда закодировать | правило в скиле |
| последнее средство | строка в CLAUDE.md |

**Доменный уровень закрывается только первыми тремя.** Текстовое правило живёт до первой длинной сессии — это пожелание, а не предохранитель.

Самая дешёвая проверка — та, которой не потребовалось: если инвариант держится констрейнтом, модель о нём не рассуждает вовсе (индекс есть — сортировки нет).

### 4. Завести кандидата в граф

Для всего, что дошло до эскалации, — узел в `graph/incidents/` по образцу существующих: обязательные `root_cause` и `pattern`, `severity` по матрице, `regression_guard` со ссылкой на предложенный предохранитель, `status: candidate`. Рёбра к коммитам и файлам допишет `build-graph.js`, руками — только суждение о причине.

Затем прогнать `validate-graph.js`: он отбраковывает вакуумные записи и укажет на инварианты-декорации.

### 5. Доложить пользователю

Только то, что прошло матрицу. Для каждого пункта: что случилось, сколько раз, чем закрыть, и во что это обойдётся. Формат — проза с конкретикой, без списка «прочих наблюдений»; если эскалировать нечего, так и сказать одной строкой.

## Побочный продукт: объективный скоуборд исполнителей

Доля записей с `trace: true` и `friction_section: true` в разрезе `agent_type` — машинная замена ручным вердиктам в `ai-usage.md`. Не «Codex справился неплохо», а «доля работ с детерминированным следом: Codex 60%, Opus 85%, планка одна». Обновлять живую таблицу там же, а не плодить вторую.

## Чего не делать

- Не оценивать «качество агента вообще» — только конкретные проблемы и следы их решения.
- Не заводить вторую систему учёта рядом с графом.
- Не эскалировать функциональный уровень: алерт-фатига убивает механику за неделю.
- Не считать отсутствие записей доказательством отсутствия проблем — пустая секция трения подлежит той же проверке на вакуумность, что и зелёный прогон без данных.
