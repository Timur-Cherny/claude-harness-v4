# QA-прогон UI на живом проекте

Зелёный экран ничего не доказывает: главные дефекты UI **молчат** — проглоченная ошибка, глухой гейт, пустой каталог, прочитанный как «данных нет». Прогон устроен так, чтобы молчание было слышно.

Границы: наблюдение со стенда ≠ факт о продукте — `local-stand-findings`; поведение задаёт конфигурация БД, не код — `code-config-driven`; найденное закрепляется тестом — `code-tests`; вёрстка/рендер — `ui-render-review`.

## 1. Матрица прогона строится ИЗ ТРЕБОВАНИЙ, не из экранов

Источник — бизнес-требования (ТЗ, задачи трекера, доска процессов), а не «пройтись по кнопкам». Каждая строка матрицы: **требование → флоу в UI → проверяемый исход**. Экран без требования — кандидат в вопрос бизнесу; требование без экрана — дефект класса «конфигурация говорит, интерфейс не отвечает» (data-driven §3).

Обязательные столбцы за пределами happy-path, по каждому флоу:
- **отказ**: неверный ввод, запрещённое действие — виден ли ЧЕЛОВЕКУ внятный отказ (тихое «ничего не произошло» = дефект, даже если сервер прав);
- **пусто**: нулевое состояние (нет строк, нет прав, нет конфигурации) — отличимо ли от ошибки загрузки;
- **повтор**: двойной клик / повторная отправка — задвоился ли эффект.

## 2. У каждого шага две половины: экран и истина

Правило сессии 11.08 (глухой скан-гейт приёмки: UI молчал, а API работал): **исход проверяется и на экране, и в источнике истины** — БД или API-ответ. Расхождение половин само классифицирует дефект:

| экран | бэк | вердикт |
|---|---|---|
| ок | ок | pass |
| ошибка/молчит | ок | **дефект фронта** (гейт, парсинг формы ответа, зеркало правила) |
| ок | мусор/нет записи | **дефект бэка или фантом** — хуже всего: UI врёт про успех |
| ошибка | ошибка | дефект бэка; фронту засчитать ЯСНОСТЬ показа |

Фантомы искать активно: после каждого мутирующего флоу — запрос к базе на остатки (двойные записи, осиротевшие строки, qty-0 сущности, незакрытые статусы). «Successfully …» на экране без строки в базе — дефект первого приоритета.

## 3. Слушать канал, который молчит

На каждом шаге держать открытыми **консоль и network** (read_console_messages / read_network_requests): 4xx/5xx, проглоченный catch, запрос без API-префикса, севший на nginx SPA (200 + index.html = «пустой каталог»). Ошибка в консоли при зелёном экране — дефект, даже если флоу «прошёл».

Известные ловушки окружения (не дефекты продукта): перекрытое окно Chrome глушит синтетический ввод (`ui-run-chrome-occlusion`); react-query в скрытой вкладке паузит ретраи — вечный loading (`react-query3-retry-pause-hidden-tab`); клики — в screenshot-pixel space фактического размера вьюпорта.

**Дефект ввода (Enter/клавиши «не работают») при синтетическом вводе не записывается без подтверждения кодом**: сначала прочитать обработчик (или греп минифицированного бандла из пода) — есть handler и зовёт ту же submit, что кнопка → артефакт окружения, не дефект. Боевой случай 11.08: «Enter глух во всех скан-полях» оказался артефактом автоматики, настоящий дефект был в наборе сравнения одного хука. Отклонённый ввод с авто-очисткой поля и баннером на таймауте выглядит «молчанием» — прежде чем писать «молча», выждать таймаут баннера на экране.

## 4. Дефект записывается воспроизводимым или не записывается

Форма находки: **репро по шагам → ожидалось (со ссылкой на требование) → получено (скрин/стек/SQL) → класс (FE / BE / данные / требование неясно)**. «Работает странно» — не находка. Классификация по таблице из §2, не по ощущению; если для класса не хватает второй половины — добыть её, а не гадать.

Дефект бэка, найденный через UI, — всё равно дефект бэка: чинится в движке, UI-шаг остаётся его репро-сценарием.

## 5. Выход прогона

1. Матрица: требование → pass / дефект №N / не проверено (с причиной). **«Не проверено» — легальная клетка, скрытая — нет**: прогон, о котором нельзя сказать «чего он не покрыл», не закончен.
2. Дефекты — в трекер по форме §4, сгруппированные по классу.
3. Для pass-клеток мутирующих флоу — доказательство чистоты базы (счётчики/запросы), штамп дата+коммит/образ.
4. Повторяющийся класс дефекта (второе появление той же причины) — кандидат в предохранитель (`friction-review`), не просто строка в отчёте.

## Чего не делать

- Не подменять прогон юнит-тестами и e2e: они доказывают код, прогон доказывает ПРОДУКТ с его конфигурацией и данными.
- Не чинить по ходу прогона: смешение ролей теряет и баги, и покрытие. Сначала карта, потом фиксы по приоритету.
- Не закрывать флоу обходом (API-вызов вместо сломанного экрана) без записи дефекта: обход — инструмент дойти до следующей клетки, а не способ получить pass.
- Не считать прогон на локальном стенде приёмкой продукта — только dev/прод-подтверждение снимает флаг «локальное наблюдение».
