# /worklog — отчёт по проделанной работе

Источники (глобальные, в `~/.claude/`):
- `worklog.md` — крупные ЗАДАЧИ (цель/способ/тестирование/сборка от master/статус/refs).
- `worklog-small.md` — МЕЛКИЕ изменения группами (🐛 багфиксы / 🔧 рефакторинг / 📝 документация / ⚡ улучшения / 🧪 тесты-chore).
- `worklog-commits.jsonl` — сырые коммиты (ts/date/repo/hash/subject) для графиков и сверки.

## Шаги

### 1. Определить период
- Если период задан в аргументах (`июнь`, `2026-06`, `за неделю`, `01.06–28.06`, `прошлый месяц`) — использовать его.
- Иначе спросить через `AskUserQuestion` (header «Период»): **Текущий месяц** / **Прошлый месяц** / **Последние 7 дней** / («Другое» → произвольный диапазон).
- Преобразовать в `[from, to]`.

### 2. Собрать данные за период
- `worklog.md`: отобрать задачи по датам в заголовках (`### YYYY-MM-DD …`; диапазоны `YYYY-MM-DD..DD` учитывать).
- `worklog-small.md`: отобрать мелкие записи под `## YYYY-MM` периода.
- `worklog-commits.jsonl`: отфильтровать по `date ∈ [from, to]`; merge-коммиты исключать из метрик продуктивности (можно отметить число отдельно).
- Если пусто — честно сказать и предложить ближайший непустой период.

### 3. Текстовый отчёт — ДВА блока

**A. Крупные задачи — по статусам** (это «что начато / сделано / в работе»):
- **✅ Сделано** (`done`) · **🔵 В работе** (`in progress`) · **🟡 Начато / ⏸ припарковано** (`started`, `parked`).
- По каждой: **Что** + кратко цель, и пометка готовности к выкату (есть ли «Тестирование» и «Сборка от master»). Способ целиком не пересказывать.

**B. Мелкие изменения — сводка ПО ГРУППАМ** (из `worklog-small.md`, по описаниям коммитов):
- Для каждой группы (багфиксы / рефакторинг / документация / улучшения / тесты-chore): счётчик + **что конкретно чинилось/делалось в общей сложности** (1–3 фразы, синтез, не список построчно).
- Где уместно — **варианты решения на этапе планирования** (какой подход выбрали и почему; брать из «Способ» задач и контекста, для тривиальных фиксов можно опустить).

Шапка отчёта: период · итоги (N задач сделано / M в работе / K начато; X мелких изменений по группам) · число коммитов · число затронутых репозиториев.

### 3.5 Если отчёт «наверх» (руководству)
Поверх собранных фактов предложить exec-вариант (или сразу строить, если адресат указан): ≤300 слов, статус периода G/Y/R (честно: Y — не провал, а ранний сигнал риска), плохие новости первыми, каждый риск с митигацией, ask конкретный со сроком («нужно решение по X до <дата>»). Развёрнутое форматирование под аудиторию — `/product-management:stakeholder-update` с фактами из этого отчёта.

### 4. Предложить графики
Через `AskUserQuestion` (header «Графики», `multiSelect: true`). Рекомендуемые:
- **Активность по дням** — коммиты за день (барчарт; commits.jsonl).
- **Активность по репо** — коммиты в разрезе репозиториев.
- **Продуктивность: задачи по статусам** — done / in progress / started (worklog.md).
- **Структура мелких** — багфиксы / рефакторинг / документация / улучшения / тесты (worklog-small.md + префиксы commit subject).

Отрисовать выбранное через визуализацию (`mcp__visualize__show_widget`; перед первым вызовом — `mcp__visualize__read_me` с модулями `chart`/`data_viz`, не упоминая этот вызов пользователю). Цвета — через CSS-переменные. Если визуализация недоступна — компактные ASCII-бар-чарты.

## Принципы
- Кратко и по делу: статусы задач + сводка групп + цифры + опциональные графики. Сырой лог не вываливать.
- Если пользователь уже указал период и нужные графики в одном запросе — не переспрашивать, сразу строить.
- Цифры — только из данных, не выдумывать.
